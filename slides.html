Recap from last week: two ways to estimate how many different items we saw

Plain HLL

m registers keep the longest run of zeros seen.
The estimate is computed from their values.

Linear counting (LC)

Count the empty registers V.
Estimate = m · ln(m / V).
Accurate while many registers are empty.

m = 2p = number of registers (the sketch's memory slots, where p is the precision in bits)

Today the border is a fixed heuristic: switch to linear counting when the raw estimate is at most 2.5 × m

E ≤ 2.5 · m   →   use linear counting

Our goal: measure the crossover and test whether one threshold fits every sketch size

We will measure

  • The true crossover c* = n*/m (* marks the exact point where LC and plain HLL tie)
  • The best practical rule threshold c using only what the sketch can see
  • How much that rule shrinks the biggest errors vs the 2.5 rule

Hypothesis

One fixed crossover (about 2.5) works for every sketch size.

n / m tells us how full the sketch is

  • m = number of registers (memory slots)
  • n / m = distinct items per register on average
  • At n / m = 0.5, random hash collisions mean some items share registers—so ~45% (theoretically ~39%) fill instead of 50%

Bigger sketches (more registers m) can rely on linear counting for much longer before switching to plain HLL

  • Hypothesis rejected: c* grows from 2.09 (p = 8, m = 256) to 3.46 (p = 16, m = 65,536)—so no single threshold fits every sketch size
  • Why: plain HLL's built-in over-estimate does not shrink with more registers m, whereas linear counting's random error shrinks as 1/√m

Conclusion: the border is not a constant; it moves from 2.1 to 3.5 items per register as the sketch grows

  • Answer: crossover c* = 2.09 (p = 8) … 3.46 (p = 16), each with a narrow 95% CI
  • Hypothesis (one fixed threshold ≈ 2.5): rejected
  • Impact at p = 14: worst case 2.71% → 1.26%, hand-over bump 2.48% → 0.50%
  • Future work: derive c(m) from theory; other hashes and real streams
